[[section-concepts]]
== Cross-cutting Concepts

Static Configuration statt dynamischer Allokation:: Alle OS-Objekte (Tasks, OS-Applications, Resources, Alarme) werden in einer `.cfg`-Datei deklariert; `build.rs` generiert daraus Rust-Konstanten. Betrifft alle Schichten gleichermaßen (siehe <<section-bausteinsicht>>, Ebene 1).
+
**Syntax-Entscheidung (Issue #7)**: OIL-inspiriert, aber bewusst vereinfacht — erkennbare OSEK/AUTOSAR-OIL-Blockstruktur (Keyword, Name, `{ KEY = WERT; }; `), ohne OILs volle Grammatik (keine `IMPLEMENTATION`/`CONFIGURATION`-Trennung, keine Objekt-Typ-Deklarationen, keine Vererbung). Zeigt AUTOSAR/OSEK-Vertrautheit, bleibt aber in vertretbarem Parser-Aufwand für #8. Grammatik (aktueller Umfang, deckt EPIC 1 STORY 1.1.1/1.1.2 — `RESOURCE`/`ALARM`/`COUNTER`-Blöcke folgen mit den Issues, die sie tatsächlich brauchen, z. B. Phase 4 für Alarme):
+
[source]
----
file       := { block } ;
block      := keyword name "{" { attribute } "}" ";" ;
keyword    := "TASK" | "OS_APPLICATION" ;
attribute  := key "=" value ";" ;
value      := integer | ident | "TRUE" | "FALSE" ;
comment    := "//" { any-character-until-newline } ;   (* zeilenweise, ignoriert vom Parser *)

(* TASK-Attribute *)
PRIORITY    = integer                 (* siehe ECUC_Os_00075 OsTaskPriority *)
SCHEDULE    = "FULL" | "NON"          (* siehe ECUC_Os_00076 OsTaskSchedule *)
APPLICATION = ident                   (* Referenz auf einen OS_APPLICATION-Namen *)

(* OS_APPLICATION-Attribute *)
TRUSTED     = "TRUE" | "FALSE"        (* siehe SWS_Os_00446 *)
----
+
Beispiel:
+
[source]
----
TASK MainTask {
  PRIORITY = 5;
  SCHEDULE = FULL;
  APPLICATION = TrustedApp;
};

OS_APPLICATION TrustedApp {
  TRUSTED = TRUE;
};
----

Schutzdomänen als Leitkonzept:: Memory Protection und OS-Applications sind kein Aufsatz auf einen fertigen Scheduler, sondern werden von Phase 0 an mitgedacht (siehe PLAN.md, Abschnitt "Startpunkt-Entscheidung"). Der Scheduler (Phase 3) entsteht *innerhalb* dieser Domänen.

Fehlerbehandlung:: Data-Abort-Handler reagiert auf Memory-Protection-Verletzungen mit einem definierten Fehlerpfad statt einem Absturz (Details: link:../req42/04-product-backlog.adoc[req42 EPIC 2], Requirements `SRS_Os_11013`/`SRS_Os_11014`).

Traceability:: Jede Anforderung ist bis zu ihrer AUTOSAR-Quelle (SWS_OS/RS_OS) oder — für rOSEK-eigene Belange wie das Boot-Fundament — bis PLAN.md zurückverfolgbar. Siehe link:../req42/README.adoc#section-traceability[req42 Traceability] für das Drei-Ebenen-Modell.

Testkonzept:: Host-Unit-Tests mit Mock-HAL für isolierbare Kernel-Logik, alles Hardware-Nahe nur auf echtem Board verifizierbar (siehe PLAN.md, Abschnitt "Testinfrastruktur").
