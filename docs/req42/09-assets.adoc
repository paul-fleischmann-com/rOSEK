Cargo-Befehle müssen aus `src/rust/` (oder einem Unterverzeichnis davon) heraus laufen (Toolchain-/Config-Discovery). **Kein** workspace-weites Default-Target mehr (Issue #8) — der Workspace mischt `#![no_std]`-Firmware-Crates mit der Host/std-Crate `rosek-config`, ein einzelnes Default-Target könnte nur für eine der beiden Seiten richtig sein:
[source,bash]
----
# Firmware (rosek-port-am335x + rosek-board-beaglebone-black):
cargo build --release --target armv7a-none-eabi -Z build-std=core -p rosek-board-beaglebone-black

# rosek-config (Parser/Codegen, Host):
cargo test -p rosek-config
----

| `src/rust/rosek-config/`
| Host/std-Crate: Lexer + rekursiv-absteigender Parser (Issue #8) + Codegenerator (`codegen`-Modul, Issue #9) für die in #7 entschiedene Config-Grammatik (`TASK`/`OS_APPLICATION`). 22 Tests, seit Issue #10 als Integrationstests unter `tests/parser.rs` (16) und `tests/codegen.rs` (6) statt inline in `src/` — alle Tests nutzen ohnehin nur die öffentliche API, `src/` enthält keinen Testcode. Darunter ein echter, dabei gefundener Bug (der Lexer klemmte überlaufende Zahlen bisher still auf `u32::MAX` statt sie abzulehnen) und ein Test, der den generierten Code tatsächlich durch `rustc` kompilieren lässt statt nur Teilstrings zu prüfen. `default-members` der Workspace, läuft also bei einem bloßen `cargo build`/`cargo test` ohne `-p`. Nie fürs `armv7a-none-eabi`-Target kompiliert.

| `src/rust/rosek-board-beaglebone-black/rosek.cfg`, `build.rs` (Codegen-Teil)
| Board-eigene Static-Config (zwei `OS_APPLICATION`s, zwei `TASK`s, Platzhalter-Inhalt bis Phase 2/3 echte Werte brauchen). `build.rs` parst sie über `rosek-config` und schreibt `$OUT_DIR/config.rs`; `main.rs` bindet das per `include!` ein und gibt die Anzahl geladener Tasks/OS-Applications beim Boot über UART aus — Ende-zu-Ende-Beleg, dass die Pipeline tatsächlich läuft (Issue #9).

| `src/rust/rosek-config-cli/`
| Eigenständiges, aus dem Workspace ausgeschlossenes Host-Tool: skriptbares `generate`/`validate` über `rosek-config`, keine TUI-Abhängigkeiten. Eigenes `rust-toolchain.toml` (`stable`) statt der gepinnten Firmware-Nightly. 5 Prozess-Level-Tests gegen das gebaute Binary (`tests/cli.rs`, über `CARGO_BIN_EXE_rosek-config-cli`).

| `src/rust/rosek-config-tui/`
| Eigenständiges, aus dem Workspace ausgeschlossenes Host-Tool: interaktiver ratatui-Editor (`edit <pfad.cfg>`) für `.cfg`-Dateien, inklusive Live-Vorschau des generierten Codes. Editier-Logik (`app.rs`) bewusst frei von ratatui/crossterm-Typen und dadurch ohne echtes Terminal unit-testbar (10 Tests). `rosek-config` bekam dafür ein `serialize`-Modul (Config → `.cfg`-Text, verwirft Kommentare — daher der jetzt vereinfachte Kopfkommentar in `rosek.cfg`). Ebenfalls `stable` statt der gepinnten Nightly, wie `rosek-config-cli`.

| `.github/workflows/release.yml`
| Goreleaser-artiges Release-Packaging für alle drei unabhängig versionierten Artefakte (Kernel-Firmware, `rosek-config-cli`, `rosek-config-tui`) als je eigenes Archiv pro Zielplattform. Läuft bei Push eines `v*.*.*`-Tags (veröffentlicht ein GitHub Release) oder manuell per `workflow_dispatch` (reiner Trockenlauf, baut/paketiert alles als Workflow-Artefakte, veröffentlicht aber nichts). Noch nicht in echtem CI verifiziert (kein Tag bisher gepusht) — insbesondere die Verfügbarkeit von `ubuntu-24.04-arm`/macOS/Windows-Runnern auf diesem Free-Plan-Repo ist eine Annahme, keine bestätigte Tatsache (siehe Kommentar im Workflow selbst).
