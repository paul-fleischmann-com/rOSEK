[[section-traceability]]
== Traceability

Requirements laufen in rOSEK durch drei Ebenen, jede mit einer anderen Fragestellung:

[cols="1,2,3", options="header"]
|===
| Ebene | Beantwortet | Fundstelle

| RS_OS (`SRS_Os_*`)
| *Warum* — Motivation/Rationale/Use Case auf Systemebene, unabhängig von einer konkreten API
| link:../autosar/rs_os/README.adoc[docs/autosar/rs_os/]

| SWS_OS (`SWS_Os_*`)
| *Was* — die technische Konkretisierung als prüfbares "shall"-Requirement; referenziert sein RS_OS-Requirement selbst über die Zeile "Upstream requirements: ..."
| link:../autosar/sws_os/README.adoc[docs/autosar/sws_os/]

| req42 Product Backlog (STORY)
| *Was für rOSEK* — die konkrete, für rOSEK formulierte Anforderung als User Story, deren "damit"-Klausel aus dem RS_OS-Rationale/Use-Case-Text abgeleitet ist
| docs/req42/04-product-backlog.adoc
|===

=== Beispielkette

`SRS_Os_11005` (RS_OS, Warum: "a task of an OS-Application may overflow its stack, causing static data of an unrelated OS-Application to be corrupted") to `SWS_Os_00198` (SWS_OS, Was: "shall prevent write access to its own data sections and its own stack from non-trusted OS-Applications") to STORY 2.2.1 (req42, rOSEK-Anforderung, EPIC 2 "OS-Application-Modell + Memory Protection") to spätere Implementierung in `rosek-core`/`rosek-hal`.

=== Verlinkungskonvention

* Jede Story, die auf AUTOSAR zurückgeht, verlinkt *beide* Ebenen wo vorhanden (SWS_Os_* *und* SRS_Os_*), nicht nur eine — RS_OS liefert die Begründung, SWS_OS die technische Präzisierung.
* Links zeigen immer auf Datei *und* Anchor, nicht nur auf die Datei: Schema `\link:../autosar/<sws_os oder rs_os>/<pfad>.adoc#<ID>[<ID>]`. Ein Link ohne Anchor-Fragment ist nur zulässig, wenn kein einzelnes Requirement, sondern ein ganzes Kapitel gemeint ist (z. B. Verweis auf ein Konfigurationskapitel als Ganzes).
* Requirement-IDs werden nicht neu abgeschrieben oder paraphrasiert kopiert — der Volltext bleibt in `docs/autosar/`, hier wird nur zitiert/verlinkt.

=== Ausnahme: Phase 0 (Boot-Fundament)

Board-Bootstrapping (Vektortabelle, MMU-Flat-Mapping, UART/GPIO-Treiber) hat **keine** AUTOSAR-Entsprechung, weil SWS_OS/RS_OS erst oberhalb eines bereits laufenden Systems ansetzen. EPIC-0-Stories verlinken stattdessen auf PLAN.md und die zugehörigen Repo-Issues. Das ist eine bewusste, dokumentierte Abweichung von der sonst durchgängigen AUTOSAR-Traceability, keine Lücke.

=== Verifikation

Jeder `link:`-Verweis auf `docs/autosar/` muss auf eine tatsächlich existierende `[[ID]]`-Anchor-Definition zeigen, und der BCC1-relevante Requirement-Umfang sollte sichtbar bleiben, auch wenn noch nicht jede einzelne AUTOSAR-Anforderung referenziert ist. Beides prüft:

[source,bash]
----
python3 tools/check-traceability.py
----

Das Skript meldet (a) jeden kaputten `link:...#ID`-Verweis unter `docs/req42/` (Exit-Code 1, falls vorhanden — CI-tauglich) und (b) eine Coverage-Übersicht je BCC1-relevantem SWS_OS-/RS_OS-Kapitel: wie viele der dort definierten Requirements bereits von einer req42-Story referenziert werden und welche (noch) nicht. Coverage-Lücken sind rein informativ und lassen das Skript nicht fehlschlagen — req42 muss BCC1 nur *mindestens* abdecken, nicht jedes Einzelrequirement zitieren.

Neue Stories mit AUTOSAR-Bezug sollten vor dem Commit mit diesem Skript geprüft werden, ebenso wie das Gesamtdokument mit `asciidoctor docs/req42/README.adoc` fehlerfrei rendern muss.
